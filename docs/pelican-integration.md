# Installed Pelican integration research

**Historical AI-written research:** see [spike findings](spike-findings.md) for current pinned-source verification and corrections. In particular, custom steps go before/after all built-in steps, and mc-router has a native mutation API with persistence limitations.

Target **the deployed Panel v1.0.0-beta38**, not moving `main`. Official [plugin documentation](https://pelican.dev/docs/panel/advanced/plugins/) warns that the system is still evolving. `php artisan help p:plugin:make` on the installed Panel exposes `--name`, `--author`, `--description`, `--category`, `--panels`, `--panelVersion`, etc.; use `php artisan p:plugin:make` in a disposable checkout, not the live Panel, when beginning implementation. A plugin should specify a Panel compatibility version and avoid core edits.

## Creation wizard (confirmed in live beta38 source)

- `app/Filament/Admin/Resources/Servers/Pages/CreateServer.php` defines `/admin/servers/create`; its `Information` wizard step contains `name`, `node_id`, `owner_id`, `allocation_id` (Primary Allocation), and `allocation_additional` repeater. The node selector resets primary allocation when the node changes. The primary selector queries unassigned allocations on the selected node; its built-in UI does **not** distinguish router-eligible game allocations from forwarded add-on ports.
- The page uses `App\Traits\Filament\CanCustomizeSteps`: `CreateServer::registerCustomSteps(StepPosition::Before|After, Step ...)` adds whole wizard steps before/after the built-in steps. It does **not** expose an insertion point inside Information. The page does not use the otherwise-available `CanModifyForm` trait. Therefore the requested precise placement and filtering of the existing primary selector are **not proven plugin-only**. A separate wizard step is accepted by the user; prototype state flow and server-create lifecycle before committing to that UX. Prefer proposing a small upstream hook if the native step cannot be made coherent; don't copy the full create page into the plugin.
- `handleRecordCreation(array $data)` calls `ServerCreationService::handle`. The service uses `allocation_id` and optional `node_id`, persists server/assignment, then asks Wings to create it; integration must respect failure cleanup and not expose a route for a server that failed creation. Do not assume an extra step field automatically reaches service payload or survives form dehydration. Recheck with a test.
- Models: `App\Models\Server`, `App\Models\Node`, `App\Models\Allocation`; use the primary `server.allocation_id` and allocation's **real private** `ip` and `port`. `ip_alias`/`address` are UI-facing; `Allocation::address` appends backend port, and installed beta38 source did not show a `show_port` switch. Do **not** promise that setting an alias yields a copyable `hostname` without the internal port; give the plugin its own join-address preview/status.
- Candidate game allocations are 25565–25574 per node; forwarded extra-port pools are 26100–26109/26110–26119. Eligibility should be an admin-configured set/range per node (or a plugin-owned classification), validated against live allocations and their assignment state at submit time. Changing node invalidates a previously selected primary allocation.

## Router seam

- Standalone mc-router v1.47.1 is launched with `-routes-config /etc/mc-router/routes.json -routes-config-watch`. [Upstream JSON format](https://github.com/itzg/mc-router#routing-configuration): `{ "mappings": { "slug.mc.kynzo.org": "192.168.1.229:25566" } }`, with `default-server` omitted. File is **root-owned** and service has `ProtectSystem=strict`; the Panel must not receive arbitrary root/file-write access. A narrowly scoped authenticated router helper/forced command should validate hostnames and backends, apply an atomic file update, and report the effective mapping. Avoid exposing the built-in mc-router HTTP API without authentication.
- The router processes Minecraft Java TCP handshake hostnames, not raw UDP or Bedrock. A DNS-only wildcard routes name lookup; the game port is still public 25565. When a backend allocation changes, re-render route and verify it; when a server is deleted/toggle disabled, delete its route only if plugin ownership matches.

## Questions to prove in a local spike

1. How to capture a new wizard field at creation and avoid overriding an admin's visible primary selection? Can a plugin step choose a router-pool allocation after node selection and show the final selection clearly without modifying core?
2. Which safe hooks/events exist in beta38 for server creation, deletion, primary-allocation changes, and node moves? If incomplete, use scheduled reconciliation as source of durability. Determine whether a node can be changed after creation in this release.
3. How to install/run the plugin in a disposable Panel matching beta38 and SQLite, and how to test Filament form behavior automatically? Pin compatibility rather than using current `main` assumptions.
4. How to update router routes without granting a web process root SSH or restarting the router on every edit? Select a helper protocol with authentication, atomicity, validation, and a readback check.
